## Objective

The M6 follow-up decisive run (2026-05-17 → 2026-05-20) cleared the
question of whether v2 substrate scales at depth. At 256d × 12 blocks
× 1 epoch on gutenberg_4gb (2.2B tokens), v2 trained cleanly: zero
NaN events across 522,200 batches, pred_frob climbing in all 12
blocks (no silent layers), err_acc halving across the run, loss(roll100)
descending throughout. The conclusion in
[`2026-05-19_depth-scaling-investigation.md`](2026-05-19_depth-scaling-investigation.md)
was explicit:

> Next experimental jump per Brian's preference would be 1024d × similar
> depth (skipping 512d intermediate) on a comparably-sized corpus.

This document scopes that jump. The 1024d × 12 blocks run is two
things at once:

1. **Width-scaling validation** — confirms v2 substrate continues to
   behave at production-relevant width, not just production-relevant
   depth. The 256d result is encouraging; the 1024d result decides
   whether the path to 4B is open or blocked.
2. **First substrate at scale that the inference-side turbo trace
   pipeline can run against.** The substrate-mismatch closure
   2026-05-25 (LuthiModel `d6b8b22` + Sanctuary `2aafc59`) means a
   1024d checkpoint loaded into SanctuaryRunner will produce real
   `error_acc` distributions through the new `PCIntensitySource`.
   That's the empirical threshold-tuning data that's been blocked
   since the slider/turbo design shipped. The training run produces
   the checkpoint; the threshold tuning is a separate downstream step.

## What we're testing

Five testable hypotheses, ranked by decisiveness:

**H1 — Stability at production width.** Train v2 1024d × 12 blocks
without NaN events, kernel failures, or divergence. The 256d run had
zero NaN; we expect the same at 1024d but it isn't a given. The
living-weight buffers are 16× larger; if there's a numerical issue
the bigger surface will surface it.

**H2 — All blocks remain active.** `pred_frob` should grow steadily
in every block across the run, mirroring the 256d trajectory
(0.34 → 3.95 by end). M6's 128d depth sweep showed pred_frob going
silent in deep blocks ("the deep blocks went quiet"); the 256d run
inverted that. 1024d should preserve the 256d pattern at minimum.

**H3 — err_acc decreases monotonically (or near-monotonically).** The
256d run saw err_acc drop from a peak of 0.0985 to 0.0067 across the
trajectory — half. The substrate learning to predict its own input is
the load-bearing PC signal. If err_acc plateaus or climbs at 1024d,
something is wrong with μPC scaling or the training rate.

**H4 — μPC exp=0.25 holds at production width.** The 256d run used
exp=0.25 (milder than Innocenti et al.'s default 0.5). The 1024d run
will use the same. If width sensitivity differs from depth sensitivity,
the exponent may need re-tuning — but the right place to discover
that is empirically, not in advance.

**H5 — Final val_loss outperforms the 256d × 12 baseline.** Like-for-
like (same corpus, same tokenizer, same μPC exp, same training budget).
The 256d run landed at val=5.0073. 1024d should land lower if the
additional capacity is doing useful work. By how much is itself
informative — large gap = capacity is binding; small gap = data
was the constraint at 256d.

**Bonus what this run enables (not a hypothesis, an artifact):**

The resulting checkpoint at `runs/m7_1024d/...` becomes the first v2
substrate at scale that SanctuaryRunner can load. Once loaded, the
turbo trace pipeline collects real `error_acc` distributions over
representative scenarios (idle / fresh input / complex problem). That
data feeds threshold tuning per
[`2026-05-25_turbo-substrate-mismatch.md`](2026-05-25_turbo-substrate-mismatch.md).

## Falsification criteria

Stop the run early if any of:

- **NaN event in loss or any per-block diagnostic.** v2's "fail loud"
  principle means a NaN should crash the training, not be silently
  recovered. Manual stop on any NaN, investigate root cause.
- **pred_frob saturation in deep blocks** (last 3-4 blocks plateau at
  < 0.5 mid-training) — repeats the M6 128d failure mode at a worse
  scale.
- **err_acc climbing past 0.15 for sustained periods** after warmup
  — the substrate is diverging, not learning.
- **Wall-clock > 14 days** without major-milestone progress — the
  compute budget is wrong; need to revisit batch size, sequence
  length, or μPC exponent.

### Choices that need Brian's input

These are the unsettled parameters. Defaults below are my recommendation;
they're informed guesses, not data-driven.

**`--n_heads`** — for d_model=1024, head_dim=64 is the typical target,
giving 16 heads. The 256d run used 4 heads (head_dim=64 too). My
recommendation: **16 heads** for consistency with head_dim=64. If you
have a reason to prefer 8 or 32, that decision goes here.

> **DECIDED 2026-05-30: 4 heads (head_dim=256), NOT 16.** This recommendation
> was made before the seed strategy was settled. M7 is seeded from M6 via the
> Net2Net width-expander, which *preserves head count* — so the seed is 4-head,
> and `--init-from` validates `n_heads` (would reject a 16-head run). Going to 16
> heads would mean a fresh, un-seeded attention and would change head structure
> on top of width, confounding the width-scaling question M7 exists to answer.
> Brian's call: keep 4 heads so M7 is a clean continuation of M6. See
> `docs/reviews/2026-05-28_concerns-for-4.7.md` (head-count blocker + decision).

**`--batch_size`** — the 256d run used 32. At 1024d the model state
is ~16× larger, which could pressure the RX 7800 XT's 16 GB VRAM. I
need to either:
- (a) run a 10-batch dry run to measure peak memory, then size
  batch_size accordingly, or
- (b) start at a safer 16 and let it work, or
- (c) start at 32 and watch — if it OOMs, restart with smaller.
**My recommendation: (a) — run a 10-batch dry run first.** Takes
~10 minutes, saves an OOM crash that would waste hours into a real
training run.

**`--lr`** — the 256d run used `3e-4`. For larger models the learning
rate is typically scaled. The μP scaling argument says lr should be
roughly invariant if μPC is correctly applied; we used μPC for
residual scaling but the rest of the model uses standard init. My
recommendation: **start with `2e-4`** (slightly lower than 256d's
`3e-4`) as the safer choice; we can interrupt and retry at `3e-4` if
the trajectory looks too slow. The cost of lr-too-low is "training
takes longer to converge"; cost of lr-too-high is "blow-up early."

**Compute / wall-clock target** — back-of-envelope, the 256d run
took 52h. 1024d is ~16× more compute per forward pass. Naïve scaling
gives ~830h ≈ 34 days, which is too long. Reality is somewhere
between 4× and 16× depending on how the kernel scales (the C++ PC
op should be near-linear in tensor size since it's mostly broadcast
multiplies and EMAs). Realistic estimate: **5-10 days wall-clock**.
- If 10 days is too long: drop to half-epoch on gutenberg_4gb
  (~1.1B tokens, still well above Chinchilla-optimal for this model
  size).
- If even that is too long: drop to gutenberg_100 (10.6M tokens) with
  more epochs — but that's a different experiment (overfitting risk
  vs. the 256d run's clean unique-exposure profile).

**My recommendation: full epoch on gutenberg_4gb, budget up to 10
days.** That preserves like-for-like comparison with the 256d
baseline. If wall-clock pressure tightens later, half-epoch is the
fallback.

**Sparse PC gating** — the C++ kernel for sparse_gate shipped 2026-05-22.
We could enable sparse_threshold=0.01 (matching the Phase 3G plan) on
this run. But:
- Sparse gating is an experimental variable; adding it confounds
  width-scaling validation.
- The Phase 3G validation should ideally happen on a controlled
  ablation, not piggy-backed on the production-scaling run.
**My recommendation: sparse_threshold=0 (off) for this run.**
Phase 3G validation is a separate planned ablation; we don't have
to bundle them.

### Estimated model size at this config

From the 256d × 12 results.json: ~36M trainable + ~58M living-weight buffers.
Linear scaling (everything is O(d²) in attention/FFN; living buffers
scale O(d²) too) gives 1024d × 12 at roughly **16× the params**:

| | 256d × 12 (measured) | 1024d × 12 (estimated) |
|---|---|---|
| Trainable | 36M | ~580M |
| Living-weight buffers | 58M | ~930M |
| Total | ~94M | **~1.5B params** |

That's between current 1024d × 2 v1 (~113M) and the 4B production
target — a useful intermediate.

  whether the path is open; it doesn't reach the destination.
